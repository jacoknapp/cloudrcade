## Portable Docker configuration

From the repository root, copy `.env.example` to `.env`, edit the values, and run
`docker compose up -d`. The image builds the pinned player overlays once;
URL, feed, branding, save folder and namespace changes are read at runtime after
container recreation. The portable example contains no personal hosts, mounts,
identity provider or Gaseous requirement. TLS is generated by the upstream image;
terminate public HTTPS at your proxy, or provide your own certificate mounts.
ROMs and BIOS files are supplied by the operator. Place games under
`./roms/<system>/roms/` (for example `nes/roms`) and BIOS files under
`./roms/<system>/bios/`; the optional 3DS app uses `./roms/3DS/`.

`WEBRCADE_PUBLIC_URL` is the public HTTPS origin; `WEBRCADE_FEED_URL` selects the
initial/native Default feed, and `WEBRCADE_CONTENT_URL` prefixes scanner-generated
ROM/BIOS/derived URLs. Relative URLs use the current site. `WEBRCADE_APP_NAME`,
`WEBRCADE_FEED_TITLE`, `WEBRCADE_FEED_DESCRIPTION`, `WEBRCADE_STORAGE_PREFIX` and
`NEXTCLOUD_SAVE_FOLDER` control branding and persisted names. Keep the namespace
and cloud folder stable on upgrades: changing them deliberately selects different
browser storage/cloud directories and does not rename or delete existing saves.

`WEBRCADE_HOST_PATH`, `WEBRCADE_ROM_PATH`, `WEBRCADE_MANAGED_PATH`, listening address
and port configure Compose mounts. The scanner uses the separate container/host
paths `WEBRCADE_ROM_ROOT`, `WEBRCADE_STATE_PATH`, `WEBRCADE_MANAGED_ROOT`, optional
`WEBRCADE_REQUIRE_ROM_MOUNT` / `WEBRCADE_REQUIRED_ROM_DIR`, and the optional metadata
settings in the example. Without metadata it uses file names. For Gaseous metadata in the integrated container, set
`WEBRCADE_METADATA_ENABLED=true`, `WEBRCADE_METADATA_DB_HOST` and optional
`WEBRCADE_METADATA_DB_PORT`, then set `WEBRCADE_METADATA_CONFIG` to your mounted
JSON file (for example `/run/cloudrcade/config/metadata.json`). Place it in the
host directory selected by `WEBRCADE_CONFIG_PATH`; its `DatabaseConfiguration`
supplies database credentials and is never included in public config or images.
Use a read-only database account and a network route to your database. Optional
`WEBRCADE_METADATA_PATH_PREFIX` maps catalog paths into the managed library.
Alternatively, mount a database socket directory read-only and set
`WEBRCADE_METADATA_DB_SOCKET` to the socket path inside the app. This explicitly
uses Unix-socket transport and takes precedence over the TCP host/port; the
database can remain bound to localhost. Its own container must also mount the
shared socket directory. Database passwords stay in the external config JSON.

The legacy `WEBRCADE_METADATA_CONTAINER` driver remains for host-run scanners;
the app's direct database mode does not require a Docker socket.
`WEBRCADE_3DS_SKIP_DIRS` / `WEBRCADE_3DS_SKIP_NAMES` are pipe-separated exclusions.
`WEBRCADE_ENABLE_3DS` can use an operator-built app mounted through
`WEBRCADE_EXTRA_APPS_PATH`; the root release image already includes the key-free 3DS app.
Encrypted 3DS games also require an external `aes_keys.txt`: configure the read-only
`WEBRCADE_3DS_BIOS_PATH` mount and its container file path `WEBRCADE_3DS_KEYS_FILE`.
See [3DS key setup](retro-azahar/README.md#runtime-decryption-keys).

The root app container includes the feed scanner. It runs at startup and then
every `WEBRCADE_SCAN_INTERVAL_SECONDS` seconds (default21600). Disable automatic
scanning with `WEBRCADE_SCAN_ENABLED=false`. For an immediate scan, run
`docker compose exec webrcade python3 /usr/local/share/cloudrcade/service.py scan`.
Only one scan can run at a time. Failed scans preserve the previous feed and
retry at the next interval. The data mount holds feeds and derived files.

## Feed refresh

The integrated scanner runs automatically alongside the web server. It
locks each scan, deduplicates supported games, validates source files and
atomically publishes feeds. Failed scans retain the last complete feed. ROMs
and BIOS stay read-only; derived PlayStation CHDs and scan state go in the data
mount. Metadata is optional and disabled by default. All paths and URLs come
from the environment.

## PlayStation disc streaming

**PlayStation and streamed 3DS games require an active internet connection during play.**
The 3DS loader streams ROMs larger than512MiB; streamed portions alone do not
make a game available offline.

Local PlayStation CHD/PBP discs load on demand using HTTP byte ranges instead
of downloading the whole disc before play. Startup probes the disc with HEAD
and fetches its first 2 MiB; the core reads other chunks as needed. An LRU keeps
at most eight 2 MiB chunks (16 MiB of resident disc bytes). Memory cards, save
states, BIOS selection, disc selection and existing feed save IDs use the
original PlayStation interfaces. This reduces disc memory and initial transfer;
a missing chunk can briefly pause play while its network request completes.

Only direct same-origin CHD/PBP files with valid binary/range headers use this
mode. External feeds, archives and servers without advertised range support
retain upstream download handling. Malformed or incomplete range responses
fail instead of being passed to the emulator as corrupt data. Streaming needs
a connection for uncached portions; previously fully cached discs still work
offline through the existing service worker. Streamed portions alone do not
make a disc available offline.

`patch-psx-stream.py` verifies the pinned PSX source SHA-256 and three hooks
before `prepare-touch.py` builds the cloud/streaming overlay. The PSX bundle
and `psx-stream.js` URLs contain content revisions. Revalidate these hooks on
an upstream image upgrade. The PlayStation implementation is independent of
the 3DS application and cores. Run `node tests/test_webrcade_psx_stream.cjs`
and `tests/browser_webrcade_psx_stream.cjs` (Playwright Chromium/WebKit with a
same-origin staged/live endpoint; see its header). No ROM source files change.

## Offline play

Open CloudRcade and load a game while online once after this update. The browser automatically keeps the library/feed and the emulator, ROM and BIOS files it loads. Fully cached games can then launch from the normal site URL or a saved game link without a connection, including after closing and reopening the browser. Use the same browser/profile; clearing site data or browser storage eviction removes these offline files. External cover artwork may be unavailable offline.

Only files actually loaded are cached; this does not download the full game collection. A disc that was only partially streamed is not a complete offline game. Missing files produce a reconnect message. Cache writes depend on available browser storage and never interrupt online play if storage is full. Where quota estimates are available, caching leaves at least 64 MiB or 5% of the quota free for saves and other site data. Existing local game-save backups and pending Nextcloud recovery remain separate from this asset cache; cloud transfers still require a connection.

`offline.js` registers `offline-worker.js` at scope `/`, allowed by the Apache header on that worker only. The worker caches the initial library shell and feed, then allowlisted same-origin static assets and complete game responses in the configured storage-prefix cache. Online requests refresh cached files; unavailable or slow servers fall back to cached copies. Library and emulator HTML keys omit launch query parameters, while feed and asset keys retain them. Cached full game files support HEAD and byte-range reads. Partial responses, redirects, login HTML, private/no-store responses, credentials, cloud APIs and authentication routes are not cached. First-visit resources are warmed after worker activation; disc warming never forces a full download. Existing caches and save stores are not purged during updates.

Run `node tests/test_webrcade_offline.cjs`. `tests/browser_webrcade_offline.py` uses Playwright, a disposable persistent Chromium profile, and a staged/live SSH tunnel to verify online loading, a full browser restart offline, real emulator launches, local-save retention, DS isolation headers, uncached errors and reconnection. Set `WEBRCADE_TEST_PORT`, `CHROME` and optionally `ONLY` (comma-separated feed types). Regenerate HTML with `prepare-touch.py`, deploy both offline scripts, and apply `rom-library.conf` before testing. Background: [service worker lifecycle and offline caching](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers).

## Recently Played

The library starts on the folder picker with **Recently Played** highlighted when it contains games. Select it to open it; returning from a game stays in the folder you were browsing. It keeps the last 20 launched games on this browser, newest first, with repeat launches moved to the front. All system folders remain available. Recently Played is hidden when no history entries match the current library; the first system folder is selected instead. It appears automatically after playing a game or receiving matching Nextcloud history.

History keeps a browser copy in the configured storage-prefix history key and syncs to `${NEXTCLOUD_SAVE_FOLDER}/settings/recently-played.v1.json` when Nextcloud is connected. Existing browser history imports on first connection. Each game carries its latest play timestamp; devices merge the newest 20 entries, retry conditional-write conflicts, and retain offline plays across browser restarts. Reloading, returning to the tab, or reconnecting refreshes cloud history. Local sync records are scoped to the connected account; changing accounts does not import the previous account’s history. Clearing browser storage removes the local copy; reconnecting restores synced history. Stable ROM/disc identities survive title changes and feed refreshes; missing games are omitted from the view. The virtual folder uses current feed artwork, launch properties and BIOS settings without altering the generated shared feed or duplicating search results.

`recently-played.js` runs only in the library. `patch-player.py` checks the pinned upstream bundle hash before exposing the two library components and React to the adapter; `prepare-touch.py` injects the library script before bootstrap. Regenerate the player bundle and HTML, then recreate webRcade to refresh the existing player file bind. Revalidate the bootstrap hook when upgrading. Tests: `node tests/test_webrcade_recent.cjs` and `node tests/test_webrcade_recent_sync.cjs`.

The library's player script URL includes a revision derived from `patch-player.py`, since local patches keep the upstream filename. HTML generation tracks both scripts, and the patched player response requires cache revalidation. Existing browsers receive library updates without clearing their saves or preferences.

## Mobile touch controller

The pull-out **Translucence** slider fades the game controls from their standard appearance to 80% fainter, while the settings tab and centered edit toolbar remain readable. Changes save automatically in this browser and carry across platforms and orientations.

Touch devices get a translucent **‹** edge tab while a game is running. The tab is hidden in the library, during loading, and in the native pause menu; layout editing keeps its tab and Save/Cancel controls available. Tap it or pull it inward to open the panel. In **Edit layout**, drag the chevron tab up/down or across to the other edge; it snaps left/right and mirrors the arrow and pull gesture. **Save**, **Cancel**, and **Reset** apply to its position together with the game buttons. Tab positions are saved per platform/orientation in browser layouts and the Nextcloud controller profile (`dock` coordinates in each layout); previous `dockSide` preferences remain a fallback for layouts without a saved tab. The closed tab and Save/Cancel/Reset buttons follow the controls’ translucence slider, with a 20% opacity minimum. The open menu and its tab stay fully opaque for readability. The drawer stays within the viewport even with its tab near the bottom. Its **Controls on/off** switch (green/gray dot) enables or disables input and hides/shows the game buttons; the chevron stays available. Game buttons are kept at least 10 CSS pixels clear of the tab, including restored positions and live edits; opening the panel hides the game controls. The choice is saved per browser. Controls start enabled on touch devices and do not appear on devices without touch. The compact drawer centers its labels and omits helper/status paragraphs. **Mute audio** silences all Web Audio output, including achievement sounds, while leaving the emulator audio clock running so muted startup still works. It requests the mixable `ambient` audio-session type where supported, allowing phone music or podcasts alongside gameplay; OS playback may need to be resumed manually. Mute is remembered in this browser and synced as the optional `muted` boolean in the Nextcloud controller profile. Reference: [Audio Session types](https://www.w3.org/TR/audio-session/#audiosession-types).

The pad supports simultaneous direction/action touches, sliding and diagonal directions, the Select–Menu–Start center row, shoulders, and the game menu. Labels follow NES/GB/GBC/GBA, SNES/DS, Genesis, PlayStation and N64 layouts. Digital consoles use a cross-shaped D-pad with eight-way input and no analog movement. N64 has an independent analog stick, D-pad and C buttons. PlayStation keeps its D-pad and adds separate left/right analog sticks when the emulator’s analog mode is enabled; changing that mode in the game settings updates the touch controls automatically. D-pad presses and stick movement are separate inputs, so both can be used together. Held inputs are released on cancel, hiding, pause, focus loss, or rotation. Gameplay controls suppress native long-press selection/magnification with both CSS and non-passive touch-event cancellation (including Safari tap-and-hold); Menu, drawer inputs and the DS screen retain native touch behavior. Keyboard and physical gamepad input remains available. The DS game screen retains its native touch handling. Missed game touches no longer open the pause menu: use **Menu**, which hides the controls and leaves the native menu usable by touch. Button sets are selected from the actual launched platform for both legacy and default Libretro cores.

Gameplay buttons and direction controls have 10 CSS pixels of invisible touch padding. Overlapping touch areas choose the nearest control; a finger can slide between action buttons, release by moving away, and return without lifting. Direction touches stay attached to their original D-pad/stick, and the smaller center dead zone responds to light movement while retaining neutral at rest. Input updates on pointer-down/move without waiting for a click. Menu still requires a direct tap. Editing uses the visible control bounds.

During a game, open **Controls → Edit layout** to drag individual buttons or the directional pad. The game pauses while editing. **Save** keeps the layout and resumes play; **Cancel** restores the previous layout; **Reset** restores the default positions for the current orientation (then Save to keep them). Layouts are saved in this browser per platform (including separate GB/GBC/GBA layouts) and separately for portrait/landscape, using screen-relative positions clamped within the viewport. Editing also works with the controls switched off, and preserves that visibility preference afterward. The editor is unavailable until a game is running.

For Nintendo DS on touch devices, the pullout menu has a **DS screens** section. **View** cycles side-by-side, reversed side-by-side, vertical, reversed vertical, top-only and touchscreen-only layouts, wrapping around. **Single screen** switches between top-only and touchscreen-only; **Dual screens** cycles the four two-screen layouts. These replace the native layout buttons above the game on mobile. The duplicate mobile pause button is hidden; the controller’s **Menu** button opens the pause menu. The native microphone control remains available. Only the two vertical layouts start at the safe-area top and fill the available safe-area width, limited by height when necessary to keep both screens visible without distortion. There is no reserved toolbar row or extra side margin; fitting updates after rotation and reload. Side-by-side, single-screen and book layouts keep the core's normal centering. Vertical places the top screen above the touchscreen with native stylus mapping. DS choices remain available with game buttons disabled and are hidden during editing or native pause menus. All three buttons remember the chosen view in the browser (`wrcad.touch.ds-view.v1`) and the existing Nextcloud controller profile (`dsView`, 0–5). Without a saved choice the game's original layout remains. Choosing a view exits rotated book mode. Desktop and other platforms retain their existing controls. The drawer scrolls in short viewports.

The digital D-pad follows RetroArch's fixed-center eight-way model and default **80% diagonal sensitivity**: each straight direction spans 50 degrees and each diagonal spans 40 degrees. Presses and drags use the same angular regions, so returning to a straight direction immediately releases the extra input. The existing small neutral center remains. Two digital D-pad touches combine and release independently; analog sticks keep proportional movement. This replaces the earlier relative-drag thresholds and retained-direction rules. References: [overlay specification](https://docs.libretro.com/development/retroarch/input/overlay/#special-button-types), [default value](https://github.com/libretro/RetroArch/blob/b0a070c746b4f1470e0bb94f3c67f3119d88da84/config.def.h#L1095), [angle calculation](https://github.com/libretro/RetroArch/blob/b0a070c746b4f1470e0bb94f3c67f3119d88da84/input/input_driver.c#L2881).

`prepare-touch.py` extracts HTML entry points from the pinned image and adds the CSS/JS in `touch/assets/`. Apache aliases those entry points to `touch/pages/`; ROMs remain unchanged; the RTC adapter below adds memory-access exports to the pinned SameBoy core. `prepare-overlays.sh` generates missing or changed HTML before deployment. The runtime adapter uses the pinned player's exposed `window.app.emulator.controllers` interface and must be checked with source maps and browser play tests when upgrading webRcade. Generated `touch/pages/` and input hashes are host-only artifacts. Assets use revalidation caching.

## Nextcloud saves

Nextcloud is controlled by runtime environment variables. Enabling Nextcloud makes **Link** available in Cloud Storage settings; enabling automatic redirect starts login when webRcade opens online. Turning automatic redirect off keeps manual Link and connected save sync working. The browser uses native Nextcloud Login Flow v2; no Authentik installation or custom Nextcloud app is required. First authorization follows the server’s normal sign-in/approval flow. The optional trusted handoff used in this deployment can reuse an existing Nextcloud/Authentik session and grant automatically.

| Container environment | Portable default | Behavior |
| --- | --- | --- |
| `NEXTCLOUD_URL` | empty | HTTPS base URL, including any Nextcloud subdirectory. Required when enabled. |
| `NEXTCLOUD_ENABLED` | `false` | Makes Nextcloud available and permits its login/save API. |
| `NEXTCLOUD_AUTO_REDIRECT` | `false` | Starts login automatically; independent of manual Link and save sync. |
| `WEBRCADE_PUBLIC_URL` | empty | This site’s HTTPS origin, used for the API Origin check. Required when enabled. |
| `NEXTCLOUD_HANDOFF` | `false` | Use the optional `retroarcade_login` app on that server instead of native approval. |
| `NEXTCLOUD_ACCESS_HEADER` / `NEXTCLOUD_ACCESS_VALUE` | empty | Optional trusted gateway hint: require the exact value in a pipe/comma-separated header before redirecting. Leave both empty without a gateway gate. The gateway must overwrite the header; Nextcloud still authorizes the actual grant. |
| `NEXTCLOUD_LEGACY_URL` | empty | Upgrade-only original server for credentials and local backups created before server scoping. Never change this alongside `NEXTCLOUD_URL`; leave empty for new installations. |

For a portable deployment, use [nextcloud.env.example](nextcloud.env.example): set `NEXTCLOUD_URL=https://cloud.example.com`, `WEBRCADE_PUBLIC_URL=https://arcade.example.com`, and `NEXTCLOUD_ENABLED=true`. Set `NEXTCLOUD_AUTO_REDIRECT=true` to start login automatically; otherwise users choose Link. Recreate the webRcade container after changing its environment. No browser bundle rebuild is required for setting changes. `config.php` supplies current settings with `Cache-Control: no-store`; an offline browser uses its last saved public configuration.

Without the optional handoff, the connection page polls while the native Nextcloud approval tab is open, then resumes the game. If the browser blocks that tab, use the visible sign-in link. The handoff uses same-tab redirects and needs the Nextcloud app to trust your webRcade origin; this deployment already has that integration.

The root Compose deployment reads `.env`; it supplies the URL, enabled/auto flags, optional handoff and trusted gateway hint. Never commit the operator env file.

Disabled or denied connections return to the original game/library URL and show: **No access has been enabled for Nextcloud. Please enable your own cloud instance.** The optional access hint avoids leaving a user on the provider’s access-denied page. Native-flow API denials return the same message. The portable native login page remains owned by Nextcloud; deployments needing automatic return from their identity provider’s own denial page must supply an access hint or integrate its denial callback. The local copy remains playable. Other cloud providers retain their own switch when supported by this site.

The browser remembers a revocable app credential for the configured server. Changing the server never forwards old credentials to the new host. Local saves are scoped to both server and user; explicit upgrade migration retains original backups. Disconnect revokes the browser credential, pauses auto reconnect until Link is selected, and leaves remote saved files in place. Interrupted automatic sign-in is attempted once per tab to avoid redirect loops.

Game saves and the native save-state slots use the configured `NEXTCLOUD_SAVE_FOLDER` in the connected user’s Nextcloud Files. Normal game saves retain a browser-local backup. Conditional uploads detect a changed remote version instead of silently overwriting another device’s save. Cloud errors are shown; the local copy is retained. Nextcloud app credentials are stored in this site’s browser storage and supplied to the same-origin PHP bridge per request; the server retains temporary login-flow state and the one-shot result until browser acknowledgement. Clearing browser site data removes the connection, not the Nextcloud saves.

`touch/cloud/` contains the Login Flow v2 and restricted WebDAV bridge. It only addresses the configured Nextcloud server and save files inside the configured save folder; no arbitrary URL proxying or folder deletion. TLS verification, session-bound CSRF checks, a 64 MB upload limit and conditional writes apply. The login-generated Nextcloud app credential itself has the account’s standard file access; folder confinement is enforced by this bridge.

`prepare-touch.py` injects the cloud adapter before the pinned webpack runtime. It wraps exported interfaces in the player and generates emulator bundle overlays with checked hooks for their internal settings, storage and SaveManager interfaces. The original image remains unchanged. Generated `cloud-main.js` files are served through `/arcade-bundles/` from the existing touch mount. Test those interfaces when upgrading. PHP sessions use the container’s temporary directory; no persistent server-side account credentials or new service are needed. The Apache `/cloud-saves/` alias serves the PHP/API and connection page from the existing touch directory mount.

Controller configuration also syncs to `${NEXTCLOUD_SAVE_FOLDER}/settings/touch-controller.v1.json`: per-platform portrait/landscape layouts, controls visibility and translucence. Save/Cancel/Reset have equal touch target sizes. Layout changes sync only after **Save**; Cancel leaves the cloud unchanged. Existing cloud settings are restored on another browser, while local-only platforms are imported on its first connection. Individual preferences and platform/orientation layouts merge independently. Simultaneous writes retry against the current cloud version; a later explicit edit wins for the same setting/layout. Offline edits remain in a browser queue scoped to the connected account and retry after reconnect/reload. Unsaved drags are kept intact if cloud settings arrive during editing. Only controller preferences are included in this JSON; connection credentials stay separate in browser storage.


### Real-time clocks

The default SameBoy GB/GBC core synchronizes MBC3 cartridge clocks (RTC cartridge types `0x0f`/`0x10`) to the device’s local hour, minute, second and weekday. It rechecks while playing, including after resume, clock/time-zone changes and save-state restoration. The cartridge’s running day count is retained and adjusted forward only as needed to match the weekday. Clock halt/latch semantics are preserved. Games without an RTC are untouched; elapsed playtime and accelerated game-world calendars are not wall clocks.

English retail Pokémon Gold, Silver and Crystal add a software offset to the cartridge clock. The adapter reads that live offset and compensates in the RTC, without rewriting player RAM, SRAM or save checksums. Other games receive the local hardware clock; their own software-defined calendars or offsets may still affect the displayed time. GBA’s mGBA and the DS core already read host local time; this adapter leaves their native clock logic in place.

Native `game.rtc` sidecars are included as `clock.rtc` inside the regular local/Nextcloud save ZIP and restored before the core starts. Existing saves without a sidecar remain loadable. Corrupt-size SameBoy sidecars are ignored. Clock synchronization also works without a Nextcloud connection.

`patch-clock-core.py` adds two libretro memory-access exports to the exact pinned SameBoy WASM. It does not modify the emulation instructions. The source SHA-256 is checked before generating `clock-core.js`/`clock-core.wasm`; a changed upstream core requires re-verifying the exports before upgrading. `prepare-touch.py` regenerates these assets and loads `clock.js` before the existing save bridge. No production saves are migrated in bulk. Run `node tests/test_webrcade_clock.cjs` to check clock arithmetic across all 512 hardware day values, software offsets, backwards clock changes and sidecar round trips.

References: [SameBoy RTC implementation](https://github.com/LIJI32/SameBoy/blob/master/Core/timing.c), [Crystal clock offset calculation](https://github.com/pret/pokecrystal/blob/master/home/time.asm), [mGBA hardware RTC](https://github.com/mgba-emu/mgba/blob/master/src/gba/cart/gpio.c), [DS host-clock reads](https://github.com/libretro/melonDS/blob/master/src/RTC.cpp).

### Save recovery and profile isolation

Regular game-save backups are scoped to the connected Nextcloud UID (or the unlinked browser profile). Each running SaveManager keeps that owner: changing accounts requires reopening the game before cloud operations; an old game's final save stays in its original local profile. Pre-upgrade unscoped ZIPs are imported only for the browser profile recorded when this version first loads, and the original ZIPs are retained. New accounts do not silently import another profile's backups.

Local ZIPs include private recovery metadata recording pending uploads and their original cloud ETag. The metadata is stripped from emulator/cloud files. On restart, pending local progress loads first and uploads only if the original remote revision still matches. Conflicts keep both copies and show the error; an older cloud copy no longer replaces pending local progress. Browser Web Locks serialize local read/write/recovery for the same profile/path where supported.

Pending uploads also retain a fingerprint of the attempted save files. If an upload response is lost, the next save or reload checks whether Nextcloud already received that attempt before sending newer local progress. Generated ZIP timestamps and `info.txt` are ignored; game data and RTC sidecars are compared. A different remote save remains protected by conditional writes.

Nextcloud login temporarily retains the one-shot poll result in the existing protected PHP session, within the login's 20-minute lifetime. Account lookup/folder-creation failures can retry without consuming the native token again. After storing the credential in localStorage, the browser acknowledges its random receipt and the temporary session copy is deleted. Regular WebDAV credentials remain request-only. A lost acknowledgement does not block an already completed connection.

Identical cloud controller settings no longer reset held touches. Cloud-only Recently Played history becomes the initial selected folder when it arrives, unless the user has already navigated; it remains closed. PlayStation CUE deduplication includes referenced tracks, and `psx-save-ids.json` retains published disc save IDs across descriptor collisions and rescans.

Regression checks: `node tests/test_webrcade_save_recovery.cjs`, `node tests/test_webrcade_controller_sync.cjs`, the existing Recent/clock tests, and `python3 -m unittest discover -s tests -p 'test_webrcade*.py'`. The isolated PHP IO regression is `python3 tests/test_webrcade_login_recovery.py` with a PHP CLI available (or `WEBRCADE_PHP` set to the interpreter command).

## Nintendo 3DS

The CloudRcade image includes the key-free `retro-azahar/` app, registered as type `3ds`. `WEBRCADE_ENABLE_3DS` controls availability and defaults to true in the release example; the browser also has a **Nintendo 3DS** experimental setting. On touch devices the controller shows a Circle Pad, an independent right C-stick, a separate D-pad and ZL/ZR, and moves the stacked screens to the top in portrait.

Automatic connection checks: `node tests/test_webrcade_autoconnect.cjs` verifies

(`WEBRCADE_TEST_PORT`, default 18446); `LIVE=1` checks deployed library/emulator

`STAGE_PLAYER` and `STAGE_NES`. It checks fresh/reused/expired login, explicit
